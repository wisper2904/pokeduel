# Amigos e convite no P2P — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lista de amigos (pedido + aceite) e convite para duelar com um toque na aba Multijogador, usando o canal do Salão que já existe.

**Architecture:** Um script novo `js/ui/friends_screen.js` (IIFE, carregado por último) guarda os dados em `localStorage`, trata pacotes `FRIEND_*` por monkey-patch de `handleIncomingSalaoMessage`, desenha a seção de amigos dentro de `#dtab-p2p` e os pop-ups com as classes `.ds-modal/.ds-panel/.ds-yn` de `duel_screens.js`. Convite reaproveita `createIntuitiveP2PRoom()` / `joinIntuitiveP2PRoom()` sem mudar o protocolo da sala. `p2p_matchmaker.js` só ganha `trainerId` na presença, o `BroadcastChannel` do Salão ligado junto com o WebSocket e a conexão no boot.

**Tech Stack:** JS global sem bundler, PeerJS + MQTT via WebSocket (brokers públicos), BroadcastChannel, Playwright para teste (scripts fora do repo, em `/tmp/claude-0/-home-user-pokeduel/88efea4c-6713-5b38-ba92-d2c77eeb218c/scratchpad/qa/friends/`).

**Spec:** `docs/superpowers/specs/2026-11-13-amigos-p2p-design.md`

Regras de `handle`:
| msg.type | condição | efeito |
|---|---|---|
| `FRIEND_REQUEST` | remetente não é amigo | `addIncoming`, pop-up |
| `FRIEND_REQUEST` | já é amigo | `sendAccept` de volta, `upsertFriend(confirmed:true)` |
| `FRIEND_ACCEPT` | remetente em `outgoing` **ou** em `friends` | `upsertFriend(confirmed:true)`, `removeOutgoing`; se veio de `outgoing`, responde `sendAccept` uma vez |
| `FRIEND_DECLINE` | remetente em `outgoing` | `removeOutgoing` |
| `FRIEND_REMOVE` | remetente em `friends` | `removeFriend` |
